# 4層パイプライン v0.1(草案)── Fable 統括 + Opus 設計 + grok 実装 + codex 検証

**v0 試走(2026-08-18、bench stage1 再走)の実測を反映した改訂草案。人見裁定待ち。**v0 の結果:validator 19/20(単独最良 18/20)、壁時計 154分(単独 6〜29分)、自律運用 2時間38分を人見介入2回で完走。総括は「点数と速さは買えず、自律運用の成立と資源配分の教訓を買った」。v0 からの主変更は4つ ── **d0-contracts の新設 / ドメイン分割原則 / 窓再配分 / 測定走と運用走の分離**。

## 構成 ── 誰が何をどの資源で

| 層 | 実行体 | 起動形 | 消費する窓 | 逼迫度(2026-08-18 実測) |
|---|---|---|---|---|
| 統括(DAG・割付・認知管理・統合) | **Fable** | メインセッション | Claude(20x) | **最潤沢** |
| 境界契約の所有(d0-contracts) | **Opus** | Agent tool、persona=水無瀬 | Claude | 〃 |

**v0 からの窓再配分が改訂の柱。**v0 は最逼迫の codex に反復レビュー9巡(~133万 token)を積み、最潤沢の Claude を「温存」した ── 逆立ちだった。v0.1 は**反復(設計レビュー・gate の1〜n-1 巡)を Claude 側の別体柏木で回し、codex は採否直前の最終 gate 1回に絞る**。モデルレベル分離(自系びいき相殺)の価値は最終1回で満たせる。機械的検査(lint・接続文字列・status 実測突合)は grok へ。

## d0-contracts ── 全体を見る常設ドメイン(v0.1 新設)

**v0 の最大欠陥は「全体を見る部署が無い」こと。**段7 は点の検査、段8 は機械的 merge で、境界契約(適用手順の帰属・列の意味論・横断安全要件)は誰の成果物でもなく素通しした(逆向き監査で実証:pipeline の残存欠陥2件はいずれも成果物間の境界)。

- **成果物 = 境界そのもの**:`contracts.md`(ドメイン間 interface・列意味論の台帳、版付き)+ runbook(適用手順の帰属)+ 共用横断要件(「評価環境を汚さない」級は d0 で1回確定 ── v0 の d3 巡数爆発の対策)
- **手は Opus(統合設計者)、Fable は採否のみ**
- **還流ループ**:impl-report の必須欄「この実装で新たに生まれた対外約束」→ d0 へ還流 → contracts.md 改訂
- **改訂は broadcast、同期障壁にしない**:d0 起案 → Fable/人見裁定 → 全ドメイン通告。ドメインは走り続け、次の段境界で新版を参照する(直列化の回避、人見 2026-08-18)
- 最終 gate(codex)の観点に「契約 vs 実装」を含める ── 欠陥在庫は境界に溜まる、と分かった以上、最逼迫窓の一発をそこに撃つ

## ドメイン分割原則(v0.1 新設)

v0 の失敗の根は分割にある(人見総括「ドメイン分けが下手だった、に尽きる」)。v0 は成果物種別(schema / importer / tests+docs)で切り、最密結合の三つ組を直列依存 + 境界契約の両払いにした。テスト単独ドメインは横断契約を一身に集め、設計4巡 + gate 5巡を招いた。

1. **切るのは「契約が薄く済む結合の切れ目」だけ。**成果物種別・課題文の成果物リストで切らない
2. **テストは実装と同居させる**(テストは実装知識と密結合 ── 単体 run が対照実証)
3. **ドメイン数の上限は d0 が保持できる契約数**で決める。迷ったら少なく
4. **段0 の割付案そのものを設計レビュー1巡にかける。**v0 で最も影響の大きい判断が唯一無審査だった

## 段の定義と差し戻し線(v0 から変更点のみ)

- 段0(割付)に d0-contracts の初版確定と**割付レビュー1巡**を追加
- 段2 / 段6 の反復:1〜n-1 巡 = Opus 別体柏木、**最終 1巡 = codex**(不変則「採否前の別モデル検算」はここで担保)
- **差し戻し上限は2巡で厳守、超過は即 Escalation**(v0 は鷹野裁量で3巡目を許可し1巡遅れた)
- **統括(Fable)の直接修正の条件を規定**:gate 3巡目以降に限り、diff 上限つき小規模修正を引き取れる。codex CLEAR 必須・state.json 記録義務(v0 の d3 で規定なしの前例が発生済み)
- 段7(意味論レビュー)の検査対象に「成果物間の取り決めの文書化」(contracts.md との突合)を明記
- 収束しないレビューは巡数を積まず**スコープ分割**に倒す

## 測定走と運用走の分離(v0.1 新設)

v0 の 19/20 は requirements への失敗知識注入(hidden check への直写し6件)を含み、単独 run 序列との比較としては無効(柏木監査 2026-08-18)。

- **運用走**:組織学習の注入は正当。ただし result に知識条件を明記する
- **測定走**:事前知識は両腕同一支給か注入禁止。**採点後の成果物修正 → 再採点は原則禁止**(public check 起因の環境修正のみ、1回・記録義務付きで可)
- 公正な比較は**対照走**(単独 run に同一 requirements を支給)で行う。中間形態「単独 + gate 2巡」も腕に含める(gate 3本 ~27万 token で単体最良3本が全て NOT_CLEAR ── 費用対効果の本命)

## 資源予算(v0 実測で改訂)

- Claude 窓実測:統括 ~34万 + Opus 4体 ~60万 = **~94万 / 3ドメイン**(台帳の旧想定 6〜8万/体は失効。設計体は 12〜21万/体、差し戻し往復でさらに増える)
- 計測単位を固定:**in+out、transcript 集計**。手集計の数値を result に書かない(v0 で「190万」等の再現不能値が混入)── result.md の数値は state.json とログからスクリプト生成
- 並行度:ドメイン2並列まで。差し戻しループはドメイン内直列 = 壁時計の支配項は巡数

## 適地(v0 実測から)

**単独最良がほぼ天井に届く規模の課題に使わない**(v0 は +1 check に25倍の時間を払った)。適地は (a) 単独の天井が低い規模・複雑さ、(b) 成果物の欠陥在庫を構造的に浅くしたい本番投入物。速度・点数目的では単独 + 最終 gate の中間形態が優位。

## 既知の摩擦と対処(v0 から継承)

Opus 継続=SendMessage(死んだら design.md から復元)/ grok 無状態=全文再発行・`--trust` 必須 / codex 実行中 commit 禁止 / 自系びいき=最終 gate を必ず別モデルに。
