# team-takano / role-takano オーケストレーション

**claude が実装層(grok)とレビュー層(codex)を逐次バトンで回す機構の正典。**動く実体は `orch/` の [orch.sh](../orch/orch.sh) / [run_turn.sh](../orch/run_turn.sh) / [notify-session.sh](../orch/notify-session.sh) と [roles/](../orch/roles/) の役割定義2枚。

実走の証跡と socket の一次資料は consumer 側(`company/tech` の `_evidence/orchestration/`)が持つ。**本書は「なぜその形か」ではなく「どう動かすか」を持つ** ── 設計の根拠は `company/tech` が正典。

## 0. 何が新しくて、何が既にあるか

**Claude 間のオーケストレーションは 2026-08-12「終了OS-HUB」で通っている。**HUB(鷹野)が C1〜C4 のワーカーへ指示を出し、各ワーカーが節目報告を返し、HUB が採否を裁いて次を振る ── **zone 移管を最後まで運んだ実績がある。**

**したがって新規に設計するものは少ない。**変わるのは3点。

| | OS-HUB(実績あり) | 今回 |
|---|---|---|
| ワーカーの起動 | **人見が GUI でチャットを開く** | **team が bash で立てる** |
| メッセージ経路 | `mcp__ccd_session_mgmt__send_message`(アプリ経由) | **ネイティブ cross-session messaging + 外部プロセスからの UDS 直送** |
| 実装層 | codex | **grok(cursor-agent)。codex は品質ゲートへ配置換え** |
| 指示系統 | HUB 一点集約 | 同じ |
| 報告の形 | 節目報告 → HUB が採否 | 同じ |

## 1. 構成 ── 三層の党派モデル

```
人見 ─── team-takano(Fable / GUI 常駐)
              │  オーケストレーション・統合テスト・プロダクト判断
              │  ◀── cross-session messaging(双方向)──▶
              └ role-takano(opus / bg / タスク単位)   ← 設計・判断・統合
                    │  orch.sh を1行叩くだけ
                    ├ 実装担当(grok = cursor-agent)  ← 手、判定しない
                    └ レビュワー(codex = gpt-5.6-sol) ← 品質ゲート、判定する
```

| 党派 | 実体 | 持つもの | 持たないもの |
|---|---|---|---|
| 1st | claude | セッション・権限・**判断** | 細部の厳密性 |
| 2nd | codex | **品質ゲート**、細部検出 | 全体視点・判断権 |
| 3rd | grok | 実装の手 | 判断・継続性・信頼 |

**claude と codex は長所を補い合うパートナー。**claude は文脈把握と判断に強く細部が雑、codex は細部の矛盾検出に強く部分最適とオーバーエンジニアリングに寄る。**grok は交換可能な外注。**成果物だけを見て、自己申告は根拠にしない。

**team だけが全体を見る。**role は自分のタスクと、team への一本の線しか持たない。

**並行度:** team 配下の claude は既定3・最大4。claude の下は grok 2並行まで。**メモリ 16→32GB は 2026-08-19。**それまで既定3で1組ずつ。**メモリが上限を決めている** ── claude 系プロセスだけで常時 4〜6GB を占め、**bg セッションはアイドルでも1本 0.75GB を積む**(性質22)。空プロセスと蘇生ジョブの掃除だけで 2.3GB が戻った実績がある(性質19・20)。

## 2. プロトコル ── 3通で足りる

**Blocker を知れるのは全体を把握している者だけ。**role は自分のタスクしか見ていないので、**Blocker を判定できないし、させない。**role は割り当てられた範囲をやって、やったと言う。**塞がっているかどうかは team が決める。**

### team → role ①「ここまでやれ」

```
[ASSIGN]
  範囲: <どこからどこまで>
  完了条件: <何が満たされたら「やった」と言えるか>
  前提: <既に決まっていること・触ってはいけないもの>
```

### role → team ②「やった」

```
[REPORT] state=DONE|UNABLE
  成果: <生成・変更したもの>
  検証: <実際に走らせた結果。実行していないなら「未実行」と書く>
  未了: <やり残し>
```

**`UNABLE` は「できなかった」であって「Blocker」ではない。**理由を添えて返すだけ。**判断は team。**

### team → role ③「承認、待機せよ」

```
[ACK] 承認。待機せよ
[ACK] 承認。次: <次の ASSIGN>
[REJECT] 差し戻し。理由: <何が足りないか>
```

**role 側に Blocker の概念を持たせない。**「待機せよ」で足りる。**要約層(inbox)は置かない**(人見裁定 2026-08-15)。role の報告は team が直接受ける。

## 3. 経路A ── claude 間 socket は外部プロセスからも喋れる

**claude でない実行体から claude セッションへメッセージは通る。**UDS(`/run/user/1000/cc-socks/<pid>.sock`)へ NDJSON 2フレーム(auth + message)を流すだけで `accept` のセッションに配送された。**codex / grok から opus へ撃つ直行経路が成立する ── 中継役の role は要らない。**

**ただし機構は差出人を保証しない。**`auth` token は配送のゲートではなく、`from` / `from-name` は完全に詐称できる。**唯一詐称できないのは `verifiedPeerPid`**(カーネルの `SO_PEERCRED` 由来)で、これは受信側の transcript に `origin` として記録される ── **受信側で機械的に照合できる。**境界は「OS ユーザー」であって「claude か否か」ではない。

**方向で挙動が違う。**claude→claude は双方向チャット(両方に見える)。**codex→claude は受信側には割り込みで見えるが、送信側 codex は購読できない**(subprocess、投げっぱなし)。**外部送信者は ACK を socket から得られない** ── `refuse` 相手は痕跡ゼロで破棄される。

## 4. 経路B ── 逐次バトンと、ペアの往復 resume

**「独立プロセスとして起動し、次段を起こして自分は死ぬ」を繰り返す。**各段は1プロセスで、終了時に state が永続する ── 落ちても resume で拾える。**ツリー(grok が codex を子に持つ)を採らないのは、同時生存でメモリが重複し、親が死ぬと子が道連れになるため。**

**重要なのは、各段が文脈ゼロで生まれるのではなく、自分の文脈を resume で復元することである。**

| | 中身 | メモリ |
|---|---|---|
| (a) 文脈ゼロ再生成 | 毎段新規、state ファイルだけ読む | 最小。**ただし意図も履歴も消える** |
| (b) 文脈共有 | 全員が全履歴を抱える | 爆発 |
| **(c) ペアの往復 resume** | **各自が自分の文脈を保持。相手の出力が自分の次の user turn として入る** | **(a) とほぼ同じ** |

**採るのは (c)。**resume は**プロセスの生存ではなく JSONL からの文脈再ロード**なので、プロセスは各段で死んだまま ── 「常に1体」は保たれる。

**(a) を採ると判断が壊れる。**しりとり6段を (a) で回したとき、レビュー担当は直前の1語しか見ておらず、ルール違反の語を出した。**同じ実行体が、全履歴を渡された途端に同じ違反を正しく検出した** ── 見えていれば判る。見えていなかっただけ。

**レビューでは (c) が必須になる。**コードだけ渡されるレビューは意図を欠く。さらに致命的なのは再レビューで、**「自分が何を指摘したか」を持たなければ「治ったか」を判定できない。**差し戻しループは resume 前提でしか成立しない。

**起動作法(実測値)。**

- grok: `cursor-agent create-chat` で **chatId を事前に確保**(claude が握れる)→ `cursor-agent --resume <chatId> -p "<本文>" --output-format text --force --model cursor-grok-4.6-high-fast`。token の置き場・モデル名・worker の刈り取りパターンは **consumer の `.harness.json` の `orch` セクション**から差す ── 個人環境のパスを harness-core へ焼かない
- codex: 初回は `codex exec <共通オプション> "<本文>"` で走らせ、**ログから `session id:` を抜いて roster へ記録**。以降は `codex exec <共通オプション> resume <session_id> "<本文>"`
- **共通オプションに `-c model_reasoning_effort="high"` を必ず入れる。**bare の `codex exec` は `reasoning effort: none` で走る
- **grok の段末で `worker-server` を刈る。**cursor は grok 本体が死んでも常駐ワーカー(約160MB)を残す

## 5. 経路C ── ラッパに閉じ込め、戻り先は推測しない

**生フレーム・鍵・socket はスクリプトに閉じ込め、codex/grok には `notify-session.sh` を叩かせるだけにする。**codex に socket コードを生成させたところ、OpenAI 側の cybersecurity フィルタで2回弾かれ、完走した調査の書き出しが落ちた。**ラッパ経由なら生成しないので踏まない**(実証済み)。既存 `codex-agent.sh` が git 境界を縛るのと同型。

**戻り先の特定は `CLAUDE_CODE_SESSION_ID` で行う。推測しない。**claude は自分の sessionId を環境変数で知っている。**「同じ cwd の最新 interactive が自分」というヒューリスティックは成立しない** ── 同じ cwd に人見の別チャットが並ぶため、実際に2セッションへ誤爆した。

**解決は3段。**sessionId 一致 → name 一致 → 後継探索。**後継探索は既定で無効にする。**「起点より後に開始」は再起動した自分だけでなく新しい別チャットも満たし、socket 側の情報では区別が付かない。**届かないことより、違う相手に届くことの方が悪い。**

**通知は唯一の経路にしない。**socket に ACK は無く、claude は割り込みでプロセスごと交代する(§8 性質17)。したがって、

1. **成果は必ず `result.md` + `done` フラグでファイルに残す。**これが本命の経路
2. 通知は**宛先を毎回引き直しながら粘る**(10回・15秒間隔)。claude の立ち直りは実測18秒
3. それでも届かなければ **`UNDELIVERED` を残す**

**実際に2回、通知が落ちても成果は拾えている。**設計としてはこの順序が正しい。

## 6. 役割は起動時にだけ焼き、以降は垂れ流す

**段ごとに枠を被せない。**役割は各実行体の初回にだけ渡し、以降は相手の出力をそのまま次段の入力にする。理由は2つ。

**第一に、枠を組むとタスクが変わるたびにラッパを書き直す羽目になる。**段ごとの分岐がある限り汎用にならない。

**第二に、枠には相手の立場が漏れる。**実装担当がレビュー基準を知っていれば、**基準に合わせて書くようになり、ゲートの検出力が落ちる。**測る物差しを被測定者に見せてはいけない。**したがって作業域には成果物と状態しか置かない。**

**不変条件はこう置いた。**作業域(`$WORK`)に置いてよいのは `task.md` / `trace.log` / `exchange.md` / `last_msg.txt` / `result.md` / `done` / `UNDELIVERED` / `notify.log` と実装担当の成果物だけ。**スクリプト・役割定義・`roster.json` は `$WORK.prompts/` か `_core/orch/` に置き、作業域へ複写しない。**実装担当は `cd $WORK` で走るので、そこに置いたものは全部読まれる ── 初期の実装は `prompt*.txt` を作業域に書き、次の版は役割定義2枚と `roster.json` を置いていた。`roster.json` はレビュワーの実行体名まで載せる。

**役割定義は2枚に集約する。**[roles/implementer.md](../orch/roles/implementer.md) と [roles/reviewer.md](../orch/roles/reviewer.md) が正典。要点だけ再掲する。

- **実装担当** ── 手であって判定者ではない。指摘は全て直す、直さないなら理由を書く。**作り直さず差分で直す。**仕様と指示が矛盾したら**黙って辻褄を合わせず、矛盾を書いて返す**
- **レビュワー** ── 実装しない。**実ファイルを読む。報告を鵜呑みにしない。報告と実物の食い違いは最も重い指摘。**粗が無ければ「指摘なし」と書く。**仕様自体が不可能なら実装担当を責めず `IMPOSSIBLE` を出す**

**逃げ道を明示的に開けることが効く。**「指摘なし」「直さない理由」「記憶にない」を書いてよいと言わないと、**埋めにくる。**実走では「指摘なし」も「記憶にない」も実際に出た ── 捏造で埋めていない。

**制御のためだけに判定を読む。**レビュワーの出力書式 `[VERDICT] APPROVE | REJECT | IMPOSSIBLE` を runner が grep し、承認なら早期終了、不可能なら仕様へ差し戻し、**上限に達しても承認が出なければ強制エスカレーション。**内容の再構成はしない ── 本文はそのまま次段へ流す。

## 7. claude が叩くのは1行

```bash
bash .claude/_core/orch/orch.sh --task <task.md> --work <dir> [--rounds N] [--seed <dir>]
```

**段割り・setsid・resume・worker 刈り・宛先解決・判定・停止は全部この下に閉じる。**claude の仕事は **task.md を書くことと、この1行を叩くことの2つ**に縮む。

**設定は起動時に一度だけ解決する。**`orch.sh` が `.harness.json` の `orch` セクションを読み、実行体・モデル・effort・token の実値を `$WORK.prompts/roster.json` へ焼く。**段ごとに `.harness.json` を探しに行かせない** ── 途中で設定が変わっても走行中の鎖は一貫する。`--rounds` を明示すれば `orch.defaultRounds` より優先する。**`orch.implementer.tokenFile` が引けなければ明示エラーで止まる**(既定値を持たせない)。

**`--no-launch` で配置だけ検算できる。**作業域と roster の用意までやって turn=1 を起こさない。

**role を bg で立てる場合のテンプレート。**

```bash
claude --bg \
  -n "role-<タスク名>" \
  --model opus \
  --effort high \
  --permission-mode bypassPermissions \
  --dangerously-skip-permissions \
  --settings '{"crossSessionInbound":"accept"}' \
  --append-system-prompt "$(cat <charter>.md)" \
  -- "$(cat <タスク仕様>.md)"
```

- **`-n` は必須。**宛先名の固定(性質6)。**ただし固定できるのは CLI 起動時だけで、GUI セッションは名前を振り直される**(性質17)
- **`--` は必須。**可変長オプションが後続のプロンプトを食う。食われると `idle — send a prompt to start` で**無言で止まる**
- **`--settings` で `crossSessionInbound` を明示。**既定は permission mode クラスから動的に決まり、bypass 系は黙って hold する
- **`--resume` で使い回さない。**役目が終わったら止め、新しいタスクには新しい role を立てる(性質 4/5)
- **止め方を先に決めておく。**bg セッションは job として登録され、`kill` では蘇る(性質20)

## 9. team 側の作法

- **宛先は sessionId で撃つ**(性質18)。名前は保険、後継探索は既定で使わない
- **`success:true` を「届いた」と読まない**(性質9)。受領が返って初めて到達確認
- **role を resume しない。**止めて立て直す
- **着信の `origin.verifiedPeerPid` を roster と照合する**(性質13・16)
- **Blocker は team の内部状態。**role には「待機せよ」としか降ろさない
- **bg role を立てたら、止め方を同時に決める**(性質20)
